# Experimental H.264 graphics

The `feature/h264-graphics` branch adds opt-in RDP Graphics Pipeline support.
Bitmap mode remains the default. In the terminal connection manager, open
Options and turn H.264 on. The choice is saved with the connection profile.
The equivalent CLI option is:

```sh
fjern connect workstation.example --user tester --graphics h264
```

Normal certificate verification and hidden password entry still apply. The TUI
can approve an unknown certificate using its existing first-use dialog. Select
`--graphics bitmap`, or turn H.264 off in Options, to use the existing bitmap
path without advertising the graphics extension.

## Negotiation and rendering

The client requests a 32-bit session and shares DRDYNVC between graphics and
Display Control. Graphics remains available when dynamic resolution is off;
clipboard retains its separate static channel. The graphics endpoint advertises
version 8.1 with SMALL_CACHE and AVC420_ENABLED, plus version 10.7 with
SMALL_CACHE and SCALEDMAP_DISABLE. Version 10.7 lets Windows send AVC444v2.

The server chooses the negotiated flags and individual graphics codecs. H.264
is therefore a request, not a promise that every update uses H.264. When the
server declines AVC420 but confirms the graphics extension, the client handles
the negotiated non-AVC updates. If the server does not open the graphics channel,
the bitmap path remains available, including 16/24/32-bit updates. Protocol or
codec errors are reported; the client does not silently drop required updates or
reconnect with weaker certificate verification.

AVC420 and AVC444v2 use persistent per-surface FFmpeg software decoders. Annex
B/SPS checks run before native decoding, constrain coded dimensions to the
current or immediately preceding graphics surface during resize, and apply a
conservative aggregate decoder-memory budget. The VM can encode H.264 in
hardware; Fjern decodes in software. AVC444v2 restores full chroma detail for
text from main and auxiliary pictures. AVC444v1 remains unsupported.

The graphics client handles surfaces, primary-output mapping, reset, fills,
copies, bounded caches, frame boundaries and acknowledgements. Only completed
frames enter the existing presentation path. ClearCodec (including NSCodec),
Progressive, Planar and raw graphics updates accompany AVC420. RemoteFX codec 3
and Alpha codec 12 are not implemented and are rejected explicitly.
The ClearCodec adapter fixes protocol parsing errors in the dependency; its MIT
notice is retained with the source. The Progressive adapter maintains surface
reference coefficients across encoding-context changes, handles both DWT layouts,
and applies difference tiles, quality upgrades and fixed-point color conversion.

ZGFX uses a checked decoder with persistent history and bounded expansion.
Graphics/display fragmentation is independent, with per-message limits and
timeouts. A malformed stream never resumes using partially corrupted decoder
state. Logs report whether H.264 decoding actually became active and summarize
completed graphics frames and codecs at disconnect, without recording pixels.

## Validation

Synthetic tests cover AVC IDR/predictive-frame continuity and colors, separate
decoder surfaces, SPS/memory bounds, graphics negotiation, lossless-region masks,
ClearCodec parsing, Progressive tiles, frame atomicity/acknowledgements, caches,
interleaved DVC fragmentation, ZGFX history and malformed streams, and 32-bit
bitmap fallback. The fixtures are generated graphics, not desktop recordings.

```sh
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo build --release --locked
```

Initial Windows tests confirmed graphics version `0x00080105` with flags
`0x00000002`, declining AVC420. The later AVC444v2 result is described below.

### Windows AVC444v2 verification on 2026-09-28

With the VM's NVIDIA RTX 3080 and Windows RDP policies
`AVCHardwareEncodePreferred=1`, `bEnumerateHWBeforeSW=1` and
`AVC444ModePreferred=1`, Windows confirmed graphics version `0x000A0701` and
sent AVC444v2 (codec `0x000F`). Windows RdpCoreTS reported AVC available and
the NVIDIA H.264 Encoder MFT enabled. The VM retains these three policy values
at the user's request.

Fjern decodes AVC444v2 with FFmpeg. OpenH264 lost reference frames in the
captured Windows stream after some updates, while FFmpeg decoded that same
stream. Live Fjern sessions subsequently displayed a readable Windows screen
and resized through 960×1056, 1280×800, 1100×700 and 800×600 without a
decoder error. A surface replacement can briefly carry an H.264 picture coded
for its previous size, so the decoder permits that preceding size while still
applying only validated regions within the current surface. The test account
was temporary; no desktop capture or password is included in the repository.

These tests verify negotiation, decoding and interactive resizing on this VM.
They do not establish a controlled FPS or bandwidth improvement over bitmap
mode. Other servers may select AVC444v1, which remains unsupported.

### Windows black-screen report on 2026-09-27

On the configured Windows host, the user reported a black screen after a click
in a live `--graphics h264` session. The RDP connection remained open, but no
further graphics updates arrived during observation. The server declined AVC420
and used ClearCodec and Progressive; that session completed 27 graphics frames
and no H.264 updates. Two bitmap sessions remained responsive to clicks. The one
with dynamic resolution enabled also confirmed a resize to 960×528 and continued
to receive bitmap updates.

A later graphics session with dynamic resolution disabled completed 94 frames,
but its visual result after clicking was not confirmed. Intervals with no updates
in that session do not by themselves establish a stall.

These observations did not establish whether the black screen originated in
the client, server, or graphics codec.

The client did contain a resize interaction that could replace a newer GFX
frame with an older bitmap when a Display Control request timed out. It now
skips speculative bitmap allocation after GFX starts and retires any earlier
bitmap fallback when the first GFX frame arrives. Regression tests cover both
orders. A completed GFX frame at the requested dimensions now confirms the
resize without requiring a separate bitmap or Demand Active event.

On 2026-09-28, the user retested the Windows connection and reported that it
worked with the H.264 option both enabled and disabled. The saved Windows
profile has H.264 and dynamic resolution enabled. This closes the observed
black-screen report for that workload; it does not establish which change
resolved it.

A logged Windows retest on the same date requested H.264 with dynamic resolution
enabled. The server declined AVC420 (`AVC negotiated: false`), and the session
completed 1,563 graphics frames with zero H.264 updates. Codec mask `0x301`
records raw, ClearCodec and Progressive updates. A remote resize to 960×528
was confirmed; the connection exited normally. Graphics processing totaled
14,476.7 ms during this approximately 90-second interactive session, with a
30.6 ms longest message. The workload was not controlled, so these figures
cannot establish a before/after performance change or isolate codec cost.

The Windows 11 test VM has an NVIDIA RTX 3080 passed through and reported by
the guest driver. Its `AVCHardwareEncodePreferred` policy was unset. A temporary
value of `1` followed by another connection, without rebooting Windows, still
produced `AVC negotiated: false`: 492 graphics frames, zero H.264 updates and
codec mask `0x301`. The policy value was removed and verified absent afterward.
Windows RdpCoreTS event 162 reported `AVC available: 0` for both new runs and
earlier graphics connections. The policy's intended behavior is
described in [Microsoft's Terminal Server policy reference](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-terminalserver#ts_server_avc_hw_encode_preferred).

At the user's request, `AVCHardwareEncodePreferred=1` was then set again and
the test VM was rebooted. Windows kept the value after restart. The subsequent
Fjern connection still had `AVC negotiated: false`; it exited normally after
1,046 graphics frames with zero H.264 updates and codec mask `0x301`. Windows
event 162 again reported `AVC available: 0`. The policy remains enabled on the
test VM as requested. This confirms that enabling this policy and rebooting the
VM did not make this client/server pairing negotiate AVC420.

Live Windows verification after the presentation optimization completed a graphics
session with 78 frames and no decoder errors. Dynamic resolution traversed
960x1056 → 1100x700 → 1600x900 → 800x600 → 1280x800. A window capture at 1100x700
showed a correctly rendered remote browser and taskbar. The clipboard channel
opened, but file/text transfers were not exercised in this run. Bitmap mode also
connected, displayed the desktop, resized to 1100x700 and disconnected successfully.

The graphics session reported 1550.8 ms total processing time and a longest message
of 58.2 ms during the resize workload. This is processing wall time, not CPU time,
network latency or measured display FPS. AVC420 was still declined (zero AVC updates);
video smoothness and an end-to-end AVC improvement remain unverified.

Workspace validation passes 210 ordinary tests. Release validation including all
three manually enabled benchmarks passes 213 tests; formatting and Clippy also
pass. A transport-level regression runs 20 frames across four surface sizes and
checks frame atomicity, untouched pixels and recycled buffers after resize.
The vendored minifb dependency still emits existing lifetime warnings; Wayland
teardown can also print attached-proxy warnings.

## Presentation performance follow-up

The RDP pipeline follow-up adds row-generation tracking to GFX output buffers
and viewer snapshots. Generations move with their pixel allocation, so recycled
buffers recover all missed changes without recomposing every unchanged row.
Surface layout changes invalidate the output; completed-frame boundaries remain
unchanged. AVC420 conversion now writes validated regions directly into the
persistent surface rather than allocating a full RGB frame and copying regions.
See [performance](performance.md#snapshot-scheduling) for transport changes and
regression coverage.

Live validation of this follow-up on the configured RDP test host authenticated
with its previously approved certificate pin, displayed GFX output and resized
to 1920x1080. That session did not negotiate AVC; native H.264 reference continuity
and regional pixel conversion were validated with the checked-in IDR/P fixtures.

Historically, the first implementation cleared the whole output and copied it twice for every
completed frame. Full-output surfaces now overwrite the buffer without an initial
clear, and the viewer exchanges pixel-buffer ownership instead of copying again.
Partial mappings still clear uncovered pixels. Surface decoder references remain
independent, and buffers from a previous resolution are resized before reuse.

A local release-mode synthetic test of 300 full-screen frames measured composition
plus viewer handoff at 3.551 → 1.785 ms/frame for 1920x1080 and 14.355 → 8.094 ms/frame
for 3840x2160. These single-run measurements exclude decoding, networking, scaling
and actual display presentation; they are not end-to-end FPS claims.

Run the current-path benchmark with:

```sh
cargo test -p linrdp-proto --release benchmark_graphics_presentation -- --ignored --nocapture
```

Disconnect logs also report total graphics-processing time and the longest graphics
message, including decompression, decoding and composition but excluding network
wait. Compare these alongside the actual codec counts when investigating stalls.
The presentation optimization has automated coverage for buffer reuse, resolution
changes and clearing unmapped output; the live resize checks above pass, while video smoothness remains to be measured.

## Progressive region reconstruction fix

A regression exposed incorrect clipping when one Progressive stream contained
multiple regions: the client applied the union of all region rectangles to every
decoded tile. A later tile could overwrite pixels belonging only to an earlier
region. Each reconstructed tile now retains its region index and is clipped only
to that region. Regions can also expose pixels from previously decoded tiles
without sending those tiles again; these are now reconstructed from retained state.

The regression sends two disjoint regions in the same tile with distinct known
grays, then a third region reusing the previous tile. It checks both retained
colors, reuse and untouched background. The first assertion failed before the
fix. This establishes a reconstruction defect; confirmation that it eliminates
the user's persistent window trails still requires repeating that live workload.
